# FoLocal 最近使用异常与重构建议

检查时间：2026-09-20 22:36–22:42（Asia/Shanghai）。安装版为 1.13.1，CFBundleVersion 为 6；源码基线为 `dc4f48a6e`。本次检查数据库、进程、界面和相关源码，没有修改订阅、代理、AI 配置或业务代码。

## 结论

**存在订阅刷新异常，并已复现文章时间被刷新覆盖的问题；目前没有足够证据证明整体性能较此前下降。**

- 461 个订阅中，82 个保留失败状态，占约 17.8%；健康设置页显示相同数量。
- 379 个订阅的连续失败计数为 0，自动刷新仍在工作，界面能打开设置并返回文章列表。
- 一组 15 篇旧文章的发布时间被统一写成本次刷新时间，导致时间线显示“几分钟前”并改变排序。
- 一个实际订阅返回 HTTP 200，但当前 XML 解析器拒绝解析。
- 数据库 `PRAGMA quick_check` 返回 `ok`。服务端 62 项现有测试通过，不代表实际订阅兼容性已经覆盖完整。

## 已确认的异常

### 1. 高优先级：刷新会改写解析失败的发布日期

实际订阅：`https://feeds.feedburner.com/TheWillWillWeb`。

上游返回繁体中文日期，例如 `週二, 1 九月 2026 12:53:00 +0000`。JavaScript `Date.parse()` 对该输入返回无效值。当前实现回退到抓取时的 `now`，更新已存在条目时又覆盖 `published_at`。

证据：

- 界面中该源的多篇文章统一显示“15 分钟前”。
- 数据库中该源共 15 篇文章，`published_at` 全部是 `2026-09-20T14:20:32.797Z`。
- 示例文章的 `inserted_at` 为 `2026-09-19T18:36:14.278Z`，说明这些记录此前已入库。
- 隔离临时数据库中，用同一篇文章、同一 GUID、同一繁体日期连续刷新两次，发布时间从 `2026-09-20T14:40:33.768Z` 变成 `2026-09-20T14:40:33.801Z`，条目数量没有增加。

源码：`apps/server/src/rss.ts:395–417`，尤其是更新语句对 `published_at` 的覆盖，以及无效日期回退到 `now` 的处理。

建议：抽出日期归一化函数；兼容可识别的非标准日期；缺少或无法解析日期时，旧条目保留原发布时间，新条目才采用固定的首次发现时间。补充缺失日期、无效日期、本地化日期、重复刷新四类回归测试。已被覆盖的记录，应在能获得可信源日期后修复，不能直接把所有记录改成入库时间。

### 2. 高优先级：部分订阅持续无法刷新

以下为同一时点的 82 个失败状态，按错误文本互斥分类；这不是整个使用期间的请求失败率。

| 类别                       | 订阅数 | 说明                                       |
| -------------------------- | -----: | ------------------------------------------ |
| 网络、TLS、HTTP/2 连接错误 |     28 | 包括断网、连接关闭、证书日期错误等         |
| HTTP 404 / 410             |     17 | 源地址或内容可能已失效，需要逐条确认       |
| 非 RSS/Atom 或解析失败     |     13 | 不能将全部归为程序错误；有的源可能返回网页 |
| 其他 HTTP 错误             |     10 | 包括 403、500、502、503 等                 |
| RSSHub 多实例均失败        |      9 | 混合出现 503 和单实例 10 秒超时            |
| 普通订阅超时               |      5 | 单次直接抓取 20 秒超时                     |
| 合计                       |     82 | 约占全部订阅的 17.8%                       |

74 个源没有记录过成功后台刷新的时间。由于存在导入数据，这不表示它们历史上从未可用，也不表示已有文章丢失。

刷新间隔为 30 分钟，但失败源采用指数退避。检查时有 76 个源连续失败 8 次，等待约 640 分钟；另一个源连续失败 9 次，等待约 1280 分钟。延迟来自现有策略，不是定时器完全停止。

源码：`apps/server/src/scheduler.ts:64–85` 对所有失败统一增加计数；`apps/server/src/rss.ts:245–255` 把普通源的 404 也描述为“route not found on instance”，容易混淆普通订阅与 RSSHub 故障。

建议：区分本机断网、临时上游错误、永久地址失效和解析错误。网络恢复后，对因断网延迟的源做限量重试；永久失败提供集中处理入口；保留按源退避，避免恢复后同时请求所有订阅。不要仅凭这次快照批量删除或暂停订阅。

### 3. 中优先级：实际 XML 内容触发解析上限

实际订阅：`https://disksing.com/index.xml`。

- 数据库保存的错误为 `Maximum nested tags exceeded`。
- 本次再次请求返回 HTTP 200，Content-Type 为 `application/xml`，响应包含 RSS/channel 和 20 个 item。
- 用项目当前安装的 `fast-xml-parser` 及 `rss.ts` 中相同选项解析这次响应，再次得到同样错误。

这确认了当前抓取/解析链无法处理该响应；尚未进一步判断是源内容异常、解析器配置边界还是依赖行为。

源码：`apps/server/src/rss.ts:18–22`、`rss.ts:258`。

建议：把该响应裁成最小失败样本，确认具体触发节点后再修复。调整时同时保留响应体大小、解析深度和耗时限制；不直接关闭解析保护。将格式识别、解析、日期归一化和入库分离，便于单独回归。

## 按优先级推进的重构

1. **先修日期稳定性与 RSS 输入兼容性。** 两者已有实际输入和复现，收益明确。
2. **将错误分类与重试策略分离。** 当前网络中断、失效地址、解析错误都会累积相同退避，恢复体验不一致。
3. **补充可持久化的诊断记录。** `getRefreshStatus()` 只保留内存中的当前/最后一次批次；数据库主要保存每个源的最后状态。界面“上次刷新 3 个源、0 个失败”与“82 个源需要处理”可以同时成立，容易误读。应明确“最近批次”与“当前全部异常”，并保存限量批次历史和耗时。
4. **按业务边界拆分服务路由。** `apps/server/src/app.ts` 同时承载 AI、订阅、条目和本地维护接口；优先提取与上述故障相关的模块。保留现有 API 契约和回归测试，不做一次性大改写。

## 修复落实（2026-09-20）

用户确认按建议推进后，已完成以下源码修复和验证：

1. **发布日期稳定性**：提取 `feed-date.ts`，支持中文月份及星期格式；日期缺失或无效时保留已存在条目的发布时间。可信的源日期重新可解析后，下次成功刷新会纠正此前覆盖的时间，不改动条目 ID、已读和收藏关联。
