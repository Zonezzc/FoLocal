# FoLocal 保存到思源：接入方案

## 结论

可以实现。按用户明确的需求，FoLocal 的剪贴以源网站为内容来源：从原文 URL 直接提取标题、正文、作者、发布时间和图片，再保存到思源。RSS 只用于发现文章链接及记录来自哪个订阅，不参与正文生成。

第一版应完成一个可靠闭环：**获取源网站原文、预览提取结果、选择笔记本和位置、图片本地化、保留来源、避免重复、保存后打开笔记**。既支持从订阅文章发起，也支持手动输入网址，后者可以完全不经过 RSS。

原文获取失败时明确提示失败或需要用户处理，不自动退回 RSS 摘要。当前“全文获取成功”的状态不能作为正文完整的证据，需要由新的原文提取链路取代这项判断。

2026-09-21：第一版已实现。实际交付范围、测试结果与使用方法见 [实现与验收记录](siyuan-clipping-implementation.md)。下文保留设计背景；标签、单次另选保存位置、文章菜单内已保存标记等扩展交互尚未加入第一版。

现有收集箱插件的网页处理对象主要是微信公众号链接，并非通用网页入口。因此，FoLocal 直接写入思源更适合当前需求；用户无需为此启用油猴或收集箱插件，思源内核服务可连接即可。

## 用户如何使用

1. 在“设置 → 集成 → 思源笔记”中配置地址、Token、默认笔记本和保存位置，测试连接并读取可用目标。
2. 在文章菜单中点击“提取原文并保存到思源”，或通过“剪贴网址”输入地址。首次保存或选择“另存到…”时，可预览提取结果、修改标题、位置和标签；已有默认设置时可一键执行。
3. 显示简短进度：访问原网页、提取正文、保存图片、写入笔记、校验结果。
4. 校验通过后显示“已保存”，提供“在思源打开”；文章菜单显示已保存状态。
5. 同一文章再次保存时，默认打开已有笔记，也可显式另存副本。第一版不自动覆盖用户已经编辑过的笔记。

标题、作者、发布时间和正文优先从原网页的正文、元信息或结构化数据中提取，缺失的字段留空或在预览中由用户补充。额外保留最终原文链接、剪贴时间及来源订阅（如果从订阅发起）。AI 摘要可以后续作为可选附加内容，不能补写原文缺失段落。

## 内容如何取得

### 第一版：从源网站直接提取

1. **固定来源和目标。** 取得文章链接或用户输入的网址，固定本次保存位置。记录请求 URL、跳转后的最终 URL 和页面声明的规范地址；规范地址需核对，不能盲目用来覆盖真实来源。
2. **优先直接获取原网页。** 使用桌面网络能力请求源站 HTML，先应用已有站点适配规则，再使用通用正文提取器。提取器读取原网页的正文与元信息，完全不需要 RSS 正文字段。
3. **必要时读取渲染后的页面。** 静态 HTML 只有页面骨架、正文由 JavaScript 加载，或需要用户登录时，在隔离的网页视图中打开原文；页面真正加载正文后，读取 DOM。也可复用用户已在 FoLocal 中打开且 URL 匹配的原网页。等待有超时上限，不无限等待“网络空闲”。
4. **提取并检查。** 使用微信等站点专用规则处理特殊内容，通用页面再用 Readability 类提取。过滤导航、广告和侧栏；识别明显的登录页、访问限制页或空结果。疑似不完整时展示预览和提示，不能仅凭字数判定完整。
5. **转换和保存。** 规范化相对地址及懒加载图片，完成资源本地化、Markdown 转换、思源写入和回读。不会将 FoLocal 当前渲染的截断文本当成原文输入。

真实抓取结果可以缓存，但必须记录最终 URL、获取时间、提取方式和提取器版本；只有来源可信的原文缓存才能复用。RSS 正文及曾被误标为全文的缓存不能进入这条链路。

### 订阅展示不完整，会怎样影响剪贴

| 原因                                     | 对剪贴的影响                           | 应对方式                                           |
| ---------------------------------------- | -------------------------------------- | -------------------------------------------------- |
| FoLocal 界面折叠或只显示列表摘要         | 不影响原文抓取                         | 只取原文链接，独立访问源网站                       |
| RSS 本身只提供摘要、部分段落或没有正文   | 不影响原文抓取                         | 不读取 RSS 正文，使用源网页 HTML 或渲染后的 DOM    |
| RSS 没有可用的原文链接                   | 无法从该条目定位源页面                 | 用户手动提供网址                                   |
| 网页需要登录、被访问限制或动态内容未加载 | 仍可能阻止完整提取，这是源网站侧的条件 | 在 FoLocal 原网页视图中由用户完成必要操作后重试    |
| 图片懒加载、下载失败或附件不可访问       | 文字可能完整，但离线图片或附件缺失     | 分开报告文字与资源状态，提供重试或明确选择只存文字 |

目前已从源码确认一个会影响第三种情况的缺口：

1. `apps/server/src/app.ts:898` 的 `/entries/readability` 仅查询数据库，返回 `content ?? description`，没有访问原文 URL。
2. `packages/internal/store/src/modules/entry/store.ts:662` 在该接口报错时才调用 fallback；成功返回摘要也会被当作 `readabilityContent` 存下，并可能复用三天缓存。
3. `apps/desktop/layer/renderer/src/hooks/biz/useEntryActions.tsx:51` 在上述调用未抛错后设置 `ReadabilityStatus.SUCCESS`，没有确认实际进行了原网页提取。

因此，剪贴必须使用独立、真实的原文提取服务，不能把上述接口当作源站全文服务。阅读器的全文功能也应逐步接入同一服务，并使旧的错误缓存失效。这是明确的代码路径问题；尚未逐个核验用户提到的订阅，不能断言所有不完整展示都由它引起。

保存界面显示“原文已提取”及资源处理状态。提取失败时提供“打开原网页处理”“重试”或“取消”；若后续提供保存书签，则作为独立、明确的操作。不存在静默保存 RSS 摘要的降级路径。

### 后续扩展：选区、整页与批量

FoLocal 桌面端的 `SourceContentView` 已使用 Electron webview 展示原网页，但当前没有完整的剪贴桥接。

原网页 DOM 提取桥接属于第一版的渲染提取能力；后续再增加“保存选中内容”、元素选择和整页保留。网页登录状态来自 FoLocal 内的真实网页会话，不能假设自动继承 Chrome 或 Safari 的登录状态。源网站不提供或无权访问的内容，不能保证取得，也不绕过网站的访问控制。

书签模式容易补充；整页保留、元素选择、多篇批量保存放在后续，避免第一版同时承担浏览器剪贴器的所有能力。

## 技术分工

| 层              | 拟新增职责                                              | 可接入的现有位置                                                                 |
| --------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 渲染进程        | 文章命令、目标选择、内容快照、预览和状态                | `modules/command/commands/integration.tsx`、`modules/settings/tabs/integration/` |
| 内容核心        | 清洗 HTML、站点规则、表格与 Markdown 转换、URL 规范化   | 复用 `@beishanfish/web-clipper-core`                                             |
| 原文提取服务    | 获取源 HTML、调度网页渲染、执行正文提取、管理原文缓存   | 新增独立 `SourceArticleService`，供阅读器和剪贴共同使用                          |
| Electron 主进程 | 保存凭据、连接思源、图片下载/上传、写入、回读、打开笔记 | 新增专用 `SiyuanService`，注册到现有 IPC 服务体系                                |
| 本地数据库      | 保存任务、文档 ID、来源指纹、图片上传结果与错误阶段     | 扩展现有 SQLite；随 FoLocal 资料库一并备份                                       |

共享核心仍依赖 DOMParser、Document 等 DOM 能力。“宿主无关”并不意味着可以直接放进没有 DOM 的 Node 主进程。第一版优先在渲染进程完成纯转换，由主进程执行网络与写入；若后续移入 worker，再显式提供 DOM 运行环境。

思源 Token 由主进程持有，网页内容只作为待处理的数据，不能接触凭据。图片请求沿用桌面代理能力；上传后的 Markdown 使用思源返回的 `assets/...` 地址，不使用 FoLocal 本机绝对路径或网页临时 `blob:` 地址。

思源官方 API 提供笔记本查询、Markdown 建文档、资源上传和文档属性等能力。创建文档返回文档 ID；图片上传还需要检查业务返回码、失败文件列表和成功路径。相同文档路径重复调用创建接口不会覆盖原文档，不能把路径当作幂等保证。[官方 API 文档](https://github.com/siyuan-note/siyuan/blob/master/docs/API.zh-CN.md)

## 保存成功的判定

第一版建议采用“图片处理完成后再建文档，最后回读”的流程：

1. 下载图片并上传思源，缓存成功路径；相同图片在同一任务中只处理一次。
2. 替换正文中的图片链接，再创建文档，保存返回的文档 ID。
3. 写入 FoLocal 来源标记和剪贴状态，回读文档内容，核对目标、来源链接与正文，并确认图片指向实际资源。
4. 校验全部通过后标记完成并展示成功。图片失败时保留任务和已上传资源记录，允许重试；若用户选择只保存文字，要明确说明图片未保存完整。

图片上传与创建文档不是一个原子事务。任务中断、写入响应丢失时，应先查询和核对；无法确认就标记“待核对”，不能直接重建文档。这样可以避免显示失败后重试又产生一篇重复笔记。

去重使用“目标笔记本 + 规范化原文 URL”，结合本地文档映射和思源中的来源属性；不同源的同一文章也能识别。没有可靠 URL 时再使用稳定条目 ID。跨项目已有笔记的去重规则需要后续统一，不应宣称第一版已经能识别所有历史剪贴。

思源未运行、Token 失效、目标笔记本关闭时，显示明确原因并保留可重试任务。保存操作不自动删除 FoLocal 文章或修改已读状态。

## 为什么自定义 HTTP 集成只适合快速验证

FoLocal 已能用模板发送文章内容，因此可以很快做出向思源创建 Markdown 文档的概念验证。但目前存在三个直接相关的限制：

- `CustomIntegrationManager.executeIntegration()` 在 `response.ok` 后就返回成功，没有判断思源响应体的业务返回码，也没有读取文档 ID 和回读。
- 该管理器只取 `entry.content`；另一条导出链路的 `getEntryContentAsMarkdown()` 则会优先采用成功的 `readabilityContent`。直接配置模板可能保存不到用户当前正在看的全文。
- 单个 HTTP 模板无法完整承担笔记本选择、图片上传、结果核验、断点重试和去重。

因此推荐复用现有“集成”入口，增加专用思源适配器；其他集成的行为保持原有契约。

## 共享核心如何随安装包发布

当前 `web-clipper-core` 标记为 `private: true`，直接导出 TypeScript 源码，两个使用方通过 `file:../web-clipper-core` 引用。FoLocal 的 GitHub 构建只检出本仓库，不能照搬这个相邻目录依赖。

第一版建议把核心的固定提交快照接入 FoLocal 工作区包，保留 MIT 许可、来源提交和可校验的同步方式；规则变更仍回到核心仓库维护，避免三个入口各自修改转换逻辑。后续如统一发布内部版本包，再切换为锁定版本依赖。

这比把整个油猴脚本或思源插件复制进 Electron 更容易测试和维护。GM API、Vue 面板和思源插件宿主 API 都有各自运行环境，不能原样视为 FoLocal 的可调用模块。

## 推荐实施顺序与验收

**前置阶段：独立原文提取服务。** 以 URL 为唯一必要输入，完成静态 HTML 提取、渲染网页提取、来源标记、结果预览和可信缓存；明确排除 RSS 摘要与旧的误标缓存。

**第一阶段：可靠的原文剪贴。** 在提取服务基础上完成思源设置、目标选择、图片本地化、来源信息、去重和回读。在源站响应相同的测试条件下，验证同一 URL 在 RSS 正文完整、截断、为空，以及完全不提供 RSS 的四种情况下，得到一致的源站提取结果。再覆盖动态页面、登录页面、普通博客、微信公众号、代码块、表格、图片及失败恢复。

**第二阶段：扩展操作方式。** 增加选区、书签、整页、批量保存和可审查的更新操作。

第一阶段的验收标准是：在真实思源目标中读回正确文档和图片，重复操作不意外新建或覆盖，失败时状态准确且可恢复。先完成这条链路，再扩展操作模式。
